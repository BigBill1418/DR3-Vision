# ADR-0019.2: Eugene site enablement for Bonus Management

**Date:** 2026-06-06
**Status:** Accepted
**Extends:** ADR-0019 (Bonus Management System), ADR-0019.1 (Bi-weekly cadence)

## Context

ADR-0019 scoped the Bonus Management System to Woodland only in V2, with the schema designed site-scoped so Eugene could be added later "in V2.1+ with no migration." Bill's decision: ship Eugene parallel to Woodland on the same Monday cutover.

The schema is already site-scoped. The work is access control, signature chain configuration, PDF site-name substitution, and Vision Dashboard tile routing.

## Decision

Eugene enables on the same Monday cutover as the Woodland bi-weekly transition. Both sites share the same pay-period calendar, the same close-and-sign timeline (ADR-0019.1), and the same M365 destination (`payroll@svdp.us`). The differences are scoped to access matrix, signature chain, processor formula, and PDF site-name.

### 1. Access matrix

| User                                                             | Woodland bonus                      | Eugene bonus |
| ---------------------------------------------------------------- | ----------------------------------- | ------------ |
| Bill (admin)                                                     | Full                                | Full         |
| Kelsey (admin)                                                   | Full                                | Full         |
| Janette (Woodland manager, `primary_site_code=woodland`)         | Full                                | **403**      |
| Morena (California operations manager, `primary_site_code=null`) | Full                                | **403**      |
| Rick (Eugene manager, `primary_site_code=eugene`)                | **403**                             | Full         |
| Operator (any)                                                   | 403 (PIN flow can't reach `/bonus`) | 403          |

Notes on the matrix:

- **Morena does NOT see Eugene.** She's California operations manager; Eugene is Oregon. Per Bill: "only Rick and an admin can see Eugene." Her `primary_site_code = null` means "both sites for California-side bonus operations," but Eugene is outside California. Functionally she gets the Woodland-only access pattern.
- **Rick does NOT see Woodland.** Bill is explicit: Rick is Eugene-only. He gets 403 on all `/bonus` routes that resolve to Woodland data.
- **Admins (Bill, Kelsey) see both sites** with a site picker at `/bonus`. Tile click in the Vision Dashboard routes to the site picker; selection persists in the session.

Implementation: extend `src/lib/bonus/access.ts` `checkBonusAccess()` to take an optional `site_code` argument. Returns `{allowed: true, sites: ['eugene']}` for Rick, `{allowed: true, sites: ['woodland']}` for Janette and Morena, `{allowed: true, sites: ['eugene','woodland']}` for admins. All bonus routes call this gate; pages and APIs both site-scope queries by it.

### 2. Eugene signature chain

| Slot                   | Primary signer | Override authority |
| ---------------------- | -------------- | ------------------ |
| Facility (Rick's slot) | Rick           | **Bill OR Kelsey** |
| Ops (Kelsey's slot)    | Kelsey         | **Bill only**      |

This maps cleanly onto the Woodland asymmetric-override pattern from ADR-0019 §5: admin can override ops; admin-or-peer can override facility. The implementation is identical — different user IDs configured per site.

Configuration mechanism: a new site-scoped lookup function `getSignatureChain(siteCode)` returns:

```typescript
{
  facility_signer_user_id: string;          // primary signer for facility slot
  facility_override_actor_user_ids: string[]; // who can override the facility slot
  ops_signer_user_id: string;               // primary signer for ops slot
  ops_override_actor_user_ids: string[];    // who can override the ops slot
}
```

For Woodland: `facility = Janette`, `facility_override = [Bill, Morena]`, `ops = Morena`, `ops_override = [Bill]`.
For Eugene: `facility = Rick`, `facility_override = [Bill, Kelsey]`, `ops = Kelsey`, `ops_override = [Bill]`.

These configurations live in a new seed table `bonus_signature_chains` keyed on `site_id`. Pre-seeded at deploy time; modifiable by admins via `/admin/users` if staff changes ever happen (out of scope for Sprint 2 to build the UI; admins can update via SQL or a future admin panel ticket).

### 3. Kelsey-as-ops-signer is structurally fine

Kelsey is `role=admin` in the seed. The access check on the sign route is "may this user occupy this slot for this site," not "is this user a manager." Admins are allowed to occupy any slot they're configured to occupy. This keeps the schema and the access layer site-agnostic and role-flexible.

For the auto-override path (ADR-0019.1 §4), if Kelsey hasn't signed the ops slot by Tue 08:30 AM PT, the system signs as **Bill** (not Kelsey). The auto-override actor is always Bill regardless of which slot or which site — Bill is the universal override actor.

### 4. Eugene bonus formula

Confirmed by Bill on 2026-06-06: the existing Eugene row in `processor_bonus_rules.csv` is correct as seeded.

```
threshold_low=50, rate_low=$1.00, threshold_high=100, rate_high=$0.25
```

Walking it for the record:

| Units handled | Formula                   | Total                            |
| ------------- | ------------------------- | -------------------------------- |
| 50            | (0 × 1.00) + (0 × 0.25)   | $0.00 (qualifying day, no bonus) |
| 75            | (25 × 1.00) + (0 × 0.25)  | $25.00                           |
| 100           | (50 × 1.00) + (0 × 0.25)  | $50.00                           |
| 120           | (50 × 1.00) + (20 × 0.25) | $75.00                           |

Materially different from Woodland: twice the qualifying rate ($1.00 vs $0.50), higher upper tier ($1.25 effective vs $0.75 effective). The calculator pulls each site's rule per ADR-0019 §1 — no code change needed beyond the access gate flipping for Eugene.

### 5. PDF site-name substitution

The bonus PDF title block contains the literal "Woodland" today. ADR-0019.1 already updates the title block to include the period number and dates. The Eugene-aware shape is:

> **DR3 [SITE] Bonus Report — Period [N]: [start] – [end], [year]**
> _Pay date: [pay_date]_

For Period 13 of 2026:

- Woodland: "DR3 Woodland Bonus Report — Period 13: Jun 9 – 22, 2026 · Pay date Jun 26"
- Eugene: "DR3 Eugene Bonus Report — Period 13: Jun 9 – 22, 2026 · Pay date Jun 26"

The site name comes from the `sites.name` column on the joined `bonus_pay_period.site` relation. No hardcoded site names anywhere — already enforced by the structure of the existing template.

All other PDF content (per-employee table, signature blocks, attestation, footer, co-branding) is identical between sites.

### 6. Vision Dashboard tile routing

The Bonus Management tile in the Vision Dashboard becomes visible to Rick. The tile's `canSeeTile()` check in `src/lib/dashboard-tiles.ts` already calls `checkBonusAccess()`; once the access function returns `allowed=true` for Rick (per §1 above), the tile appears.

Tile click routing:

- **Single-site users (Janette, Morena, Rick):** tile click goes directly to `/bonus` which auto-resolves to their site.
- **Admins (Bill, Kelsey):** tile click goes to `/bonus` which renders a site picker (Woodland | Eugene). Selection sets a `bonus_site` cookie or session field. Subsequent bonus routes within the session honor the picked site until the admin clicks a "switch site" link in the bonus shell header.

Implementation: `/bonus/page.tsx` server component detects multi-site access and renders the picker; single-site access redirects to `/bonus?site=<resolved>`. The site picker writes a session-scoped field that all sub-routes consult.

### 7. Eugene roster bootstrap

Rick adds Eugene processors via `/bonus/employees` on day 1 (or a few minutes after sign-in on Mon Jun 8 morning, before first daily entries).

Alternative: if Bill provides a CSV roster of Eugene processors in advance, drop it into `prisma/seed/bonus_employees_eugene.csv` and the deploy seed step picks it up. Schema is identical to Woodland's roster.

Default if no seed CSV: Rick adds them through the UI. Time cost: ~30 seconds per processor, 5-15 processors typical for Eugene = under 10 minutes total.

### 8. Pay periods shared between sites

The SVdP 2026 Payroll Calendar applies to both sites — both Woodland and Eugene processors are SVdP employees on the same payroll cadence. The seed `prisma/seed/bonus_pay_periods_2026.csv` populates 26 periods for BOTH sites with identical dates. A separate site-scoped row pair per period preserves the site-scoping principle (every domain row carries `site_id`).

If SVdP ever changes pay cadence for one site but not the other (unlikely but possible), the schema accommodates: each site's periods are independent rows. Today they're synchronized.

### 9. Eugene auto-override actor: still Bill

The auto-override actor for Eugene at Tue 08:30 PT is **Bill**, same as Woodland. Bill is universal. Kelsey is NOT used as a backup auto-override actor for two reasons:

- Single-actor escalation is simpler to reason about and test
- Kelsey's role is "ops signer" — using her as the auto-override would conflate "supposed to sign" with "system fallback," which is a category error

If Bill is truly unreachable (locked account, deactivated user), the auto-override fails. The 07:30 AM urgent ntfy goes to Bill + Morena (Woodland) and Bill + Kelsey (Eugene), so a human override path is always available 60 minutes before the auto-override deadline.

## Alternatives considered

- **Two separate Entra app registrations, one per site.** Rejected. Schema and code are already site-scoped; deploying a second app would double admin overhead for zero isolation benefit (same trust boundary).
- **Kelsey as ops signer when she's not technically "ops" by title.** Kelsey is admin with cross-site visibility, which functionally makes her the ops-equivalent for Eugene. The schema is role-flexible by design; this is the intended use.
- **Eugene goes live a week after Woodland.** Rejected by Bill — "this will all go live monday." Both sites enable together.
- **Per-site separate signature-request email destinations** (e.g., `payroll-eugene@svdp.us`). Rejected — SVdP payroll is one team for both sites. Single destination `payroll@svdp.us`.
- **Eugene calculator differs from Woodland and needs a separate function.** Rejected — the existing `calculateDailyBonus()` already takes a rule from `processor_bonus_rules` keyed on `site_id`. No code change needed beyond the access gate.

## Consequences

- The Vision Dashboard tile matrix gains Rick visibility. Rick now sees: Bonus Management (Eugene only), Operations Dashboard, Compliance, Reconciliation, Exports. (No Admin & Audit; no Woodland.)
- Per-employee history and annual aggregate views work identically for Eugene — same code path, site-scoped queries.
- Audit log volume doubles roughly (Eugene generates its own audit chain). Indefinite retention unchanged.
- The bonus PDFs are site-distinguishable in payroll's inbox by subject line and title. SVdP payroll can auto-filter or sort by site if desired.
- Future second-jurisdiction enablements (hypothetical e.g. a third site) inherit this pattern. The `bonus_signature_chains` table is the configuration surface for each new site.
- Operational dependency: Rick's Entra account must be active for facility signing at Eugene. If Rick is out, Bill or Kelsey override via the existing UI.
