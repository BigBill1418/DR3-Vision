# ADR-0019.5: The em dash that ate the payroll alert

**Date:** 2026-08-11
**Status:** Accepted
**Extends:** ADR-0036 (ntfy transport), ADR-0037 (noise policy)
**Mirrors:** noc-master ADR-0063 §1 — and answers its open question
**Explains:** the `[escalation] stranded ntfy dropped (primary+fallback failed)` event of 2026-08-05

## Context

ADR-0019.4 shipped a standing signature-chain indicator on the reasoning that a
safeguard whose only output is a page can be silenced by the pager. It cited,
without explaining, this line from the app on 2026-08-05:

```json
{
  "level": 40,
  "time": "2026-08-05T16:00:01.621Z",
  "periodEnd": "2026-08-03",
  "msg": "[escalation] stranded ntfy dropped (primary+fallback failed)"
}
```

That page was the only notification that Eugene's Period 16 had missed its
payroll window. It was lost, and the period was signed roughly 25 hours late.
This ADR is the root cause.

### Root cause

HTTP header values are ByteStrings — latin-1, one byte per character. Node's
undici throws when a header value holds a codepoint above 255:

```
TypeError: Cannot convert argument to a ByteString because the character at
index 43 has a value of 8212 which is greater than 255
```

8212 is U+2014, the em dash. The stranded page's title was:

```ts
title: `URGENT: bonus period STRANDED — ${period.site.name} Period ${period.period_number}`;
```

`buildHeaders()` put that straight into `X-Title` unencoded.

Three properties of that throw explain everything observed:

1. **It happens at `Request` construction, before any socket opens.** No DNS, no
   TLS, no auth, no rate limit. The network was never involved, which is why the
   ntfy server looked perfectly healthy — VLM, CallSign and InfraWatch all
   delivered inside the same three minutes.
2. **The fallback builds the same header**, so it threw identically. "Primary
   and fallback both failed" was not two independent failures; it was one
   deterministic failure counted twice.
3. **`postWithTimeout` ended in `catch { return false; }`** — an empty catch. The
   `TypeError` was discarded, so the caller could only report an unexplained
   "dropped". The defect was invisible for as long as nobody read the source.

Reproduced directly:

```
$ node -e "new Request('https://x/', {headers:{'X-Title':'STRANDED — Eugene'}})"
TypeError: Cannot convert argument to a ByteString ... value of 8212
```

Latin-1 characters (`é`, U+00E9 = 233) pass fine. It is specifically
codepoints > 255 — and every alert title in this repo used an em dash as its
separator.

### Blast radius

This was never one alert. A sweep of the repo found **two independent publishers
with the defect and three more one em dash away from it**:

| Publisher                            | State on 2026-08-11                                                               |
| ------------------------------------ | --------------------------------------------------------------------------------- |
| `src/lib/ntfy.ts`                    | **Broken.** ~18 call sites, essentially every app alert title carries an em dash. |
| `src/lib/mymrc/ntfy.ts`              | **Broken.** Hardcoded `${kind} — ${site}` — _every_ MyMRC alert was dropping.     |
| `scripts/bonus-eod-check.mjs`        | ASCII today, unsanitized.                                                         |
| `scripts/bonus-escalation-check.mjs` | ASCII today, unsanitized. **This publishes the app-independent backstop pages.**  |
| `scripts/migrate-with-ntfy.mjs`      | ASCII today, unsanitized.                                                         |

The escalation daemon matters most: it pages when the _app_ is down. A dropped
page from that layer has nothing behind it.

Consistent with the evidence — the retained ntfy server cache (7 days) holds
only ASCII-titled DR3 messages (`Migration applied …`, `Container started`).
Every em-dash-titled alert in that window is absent.

### This is the fourth re-discovery

The fleet has fixed this exact class three times before: the bash/Python helpers
on 2026-05-06, and noc-master's Node publisher in ADR-0063 on 2026-05-22, after
an em dash in `— cordoning` swallowed a genuine host-saturation alert. ADR-0063
closed with this open question:

> Should `toHeaderSafe()` be lifted into the shared bash/Python helpers as a
> single fleet utility? They were patched independently in 2026-05-06; a shared
> implementation would prevent a fourth re-discovery.

It was not lifted. This is the fourth re-discovery. Every previous fix was
per-publisher, so the next publisher written re-introduced the defect — which is
the actual lesson: the bug is not the em dash, it is that each publisher owns its
own header construction and nothing structurally connects them.

## Decision

### 1. One sanitizer, at a relative path both bundles can reach

`src/lib/ntfy-header-safe.ts` exports `toHeaderSafe()`, mirroring ADR-0063 §1's
transliteration set plus `→` (DR3 period labels are written `2026-07-21→08-03`).
It transliterates the punctuation these titles actually use — em/en/minus dashes
→ `-`, curly quotes, ellipsis → `...`, `≥`/`≤`, `×`, `→`, exotic spaces — then
hard-replaces any residual codepoint > 255 with `?`.

The backstop matters more than the table. An unmapped glyph must degrade to a
sendable page, never a lost one.

The module has **zero imports and zero Node built-ins**, deliberately:
`src/lib/ntfy.ts` documents that it must stay bundleable for edge/browser
targets, and `src/lib/mymrc/ntfy.ts` compiles under `tsconfig.mymrc.json` which
has no `@/` alias. A dependency-free module at a relative path is the only shape
both can consume. `scripts/ntfy-header-safe.mjs` is its plain-JS twin for the
dependency-free cron daemons, pinned equal by test.

**Applied at each publisher's single choke point**, after all headers are
assembled — never per-field at call sites. Per-field is what let this survive
three fixes. `Authorization` is excluded: a bearer is ASCII by construction and
mangling it would turn an encoding bug into an auth bug. Bodies are untouched;
they are UTF-8 and may hold anything.

### 2. A drop always says why

`postWithTimeout` now records the failure class and message
(`lastPublishFailureReason()`), and the dropped paths log it:

```
[ntfy] primary AND fallback both failed - page dropped
  { topic, fallbackTopic, reason: "TypeError: Cannot convert argument to a ByteString..." }
```

A swallowed error is not a smaller failure; it is the same failure with the
evidence removed. Had the reason been logged on 2026-08-05, this would have been
a ten-minute diagnosis instead of an archaeology exercise.

`console.error` with a JSON payload rather than the pino logger, because
`@/lib/observability/logger` imports pino and `node:crypto` and documents that it
must not be reached from edge code — which `ntfy.ts` must remain safe for.

### 3. The counters stop lying (closes ADR-0019.4's residual #2)

`RunEscalationResult.ntfyPublished` counted publishes _attempted_. On 2026-08-04
the t3 fire logged `ntfyPublished:1` for a page that was thrown away inside the
process and never left it. Every escalation publish now routes through
`recordPublish()`, which increments `ntfyPublished` only on a delivered or
deliberately-cooldown-suppressed outcome, increments a new `ntfyDropped`
otherwise, and logs the reason. Same honest-ledger principle as ADR-0019.4's
`paged=false`.

### 4. A structural guard so there is no fifth re-discovery

`src/__tests__/ntfy-header-safety-sweep.test.ts` walks `src/` and `scripts/`,
finds every file that sets an `X-Title` header, and asserts each routes through
the shared sanitizer. A sixth publisher fails this test on the day it is written,
rather than on the payroll morning it is needed.

It also asserts a floor on the number of publishers found — an empty sweep would
otherwise pass every assertion while checking nothing.

## Alternatives considered

- **RFC 2047 encoded-words (`=?UTF-8?B?…?=`).** Rejected. It is the correct
  answer for MIME headers, but ntfy does not decode it, so the operator would
  see literal `=?UTF-8?B?…?=` on their phone. The fleet already chose
  transliteration in ADR-0063; matching it keeps one convention.
- **Strip non-ASCII entirely.** Rejected — `STRANDED  DR3 Eugene` reads as a
  typo. Transliteration keeps the sentence.
- **Ban non-ASCII in titles by lint.** Kept as a _secondary_ assertion, not the
  primary defence. A lint rule cannot see a title interpolated from a database
  value (a vendor name with an accent, a site renamed with an en dash), so the
  runtime sanitizer has to exist regardless.
- **Sanitize at every call site.** Rejected — that is the shape that failed three
  times. The choke point is the whole point.
- **Fix only `src/lib/ntfy.ts`** (the publisher that dropped the Eugene page).
  Rejected — the sweep found MyMRC in the identical state and three daemons one
  character away. Fixing the instance and leaving the class is what produced a
  fourth re-discovery.

## Consequences

- Every alert this repo publishes can now contain arbitrary Unicode in its title
  and still deliver. The em-dash class is closed for all five publishers.
- **MyMRC alerting starts working.** It has been silently dropping every page it
  raised. Expect previously-unseen MyMRC alerts to begin arriving; they are not
  new failures, they were always happening.
- A dropped page is now diagnosable from one log line.
- Escalation run summaries are truthful about delivery.
- The 2026-08-05 stranded page would deliver today. The condition that produced
  it (a period past its window) is already covered by t4's daily re-page and now
  additionally by the ADR-0019.4 standing indicator.
- **Unresolved, and worth stating:** the fleet still has four independent copies
  of this fix (bash, Python, noc-master Node, DR3-Vision TS + mjs). This ADR
  consolidates the two inside _this repo_ and pins them equal by test, but the
  cross-repo consolidation ADR-0063 asked for remains undone. The next repo to
  grow a publisher will re-introduce this unless that happens.
- **Also unresolved:** ntfy delivery is still unverifiable end-to-end from the
  publisher's side — a 200 from the server proves acceptance, not that a phone
  displayed anything.
